# Параллельный поиск максимума в Go

Учебный проект: сравнение однопоточного и многопоточного поиска максимального
элемента в большом массиве случайных чисел на Go с использованием горутин
и `sync.WaitGroup`.

**Автор:** Полина Пятышина 
**Стек:** Go (стандартная библиотека: `math/rand`, `sync`, `time`, `testing`)

## Что было сделано

- Реализована генерация массива из 100 000 000 случайных положительных чисел
  (`generateRandomElements`).
- Реализован однопоточный поиск максимума (`maximum`).
- Реализован параллельный поиск максимума: массив делится на `CHUNKS = 8`
  частей, каждая обрабатывается в отдельной горутине, результаты собираются
  через `sync.WaitGroup` (`maxChunks`).
- Написаны unit-тесты на все три функции.
- Добавлены бенчмарки `BenchmarkMaximum` и `BenchmarkMaxChunks`.
- В `main` выводится сравнение времени однопоточного и параллельного поиска.

## Идея

Поиск максимума хорошо распараллеливается: массив делится на независимые куски,
каждый обрабатывается своей горутиной, после чего из локальных максимумов
выбирается глобальный. Для ожидания завершения всех горутин используется
`sync.WaitGroup`. Каждая горутина пишет в свой индекс слайса `chunkMax`,
поэтому мьютекс не нужен — гонки данных нет.

## Функции

| Функция | Назначение |
|---------|------------|
| `generateRandomElements(size int) []int` | генерирует слайс из `size` случайных положительных чисел |
| `maximum(data []int) int` | однопоточный поиск максимума |
| `maxChunks(data []int) int` | параллельный поиск максимума по `CHUNKS` горутинам |

Константы: `SIZE = 100_000_000`, `CHUNKS = 8`.

## Запуск

```bash
go run .
```

Пример вывода:

```text
Генерируем 100000000 целых чисел
Ищем максимальное значение в один поток
Максимальное значение элемента: <число>
Время поиска: <N> мкс
Ищем максимальное значение в 8 потоков
Максимальное значение элемента: <число>
Время поиска: <M> мкс
```

Оба результата должны совпадать, время параллельного поиска обычно меньше.

## Тесты и бенчмарки

```bash
go test ./...
go test -bench=. -benchmem
```

Покрытые сценарии: пустой слайс, один элемент, несколько элементов, все элементы
равны, массив меньше `CHUNKS`.

## Вывод

На больших массивах параллельный вариант с 8 горутинами работает быстрее
однопоточного за счёт использования нескольких ядер CPU. На маленьких массивах
выигрыша может не быть из-за накладных расходов на создание горутин и
синхронизацию.
